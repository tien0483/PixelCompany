review-slash-commands-resolve-against-a-checkout-that-lacks-the-branch
- The Review tab's chat is a one-shot `claude -p` whose cwd is the *reviewed project's* checkout (`resolveReviewAgentCwd` → the active workspace path), while its subject — a merge request branch — is never fetched or checked out and exists only inside the prompt. Any slash command passed through to the CLI therefore resolves against the wrong thing, and each of the three built-ins failed differently for that one reason: `/understand-diff` is an agent-stack skill that only exists where `link-stack-skills.mjs` ran, so in `akselos-dev` (whose `.claude/skills` holds `create-tests`, `implement-papp`, `review-papp`, `spawn-subagent`) the CLI answered `Unknown command: /understand-diff` and the turn silently produced nothing; `/security-review` is "the pending changes on the current branch", found a clean tree, and asked the reviewer to check the branch out; `/code-review` widened to the whole branch diff and tripped the upstream rate limit on a large MR. `/simplify` worked throughout, which is what makes this look like four unrelated bugs.
- Fix shape: `review/review-command-expansion.ts` rewrites those three into locally-authored scoped instructions before `buildChatPrompt` runs, so the prompt no longer opens with a slash and there is nothing left for the CLI to expand. Do **not** add `/simplify` or a project's own `.claude/commands` entry to that map — the first is a built-in skill that already scopes itself to the code it is shown, and the second was written for that repository by its team.
- The prompt's first line is load-bearing in both directions: a pass-through command *must* be first to register as one, which is why context is appended below it, and an expanded command must *not* start with `/`. `buildChatPrompt` also re-sends the whole context block for an expanded command even mid-conversation — its instruction is "answer from what is below", and a resumed session's diff and graph brief belong to whatever file was on screen when the conversation started.
- `expectSuggestions` is still computed in the frontend (`isReviewCommandPrompt`) from the reviewer's raw text, so it is unaffected by the expansion — but that means the two lists have to stay in step: a command the runtime expands and the composer does not list produces prose the panel cannot turn into a draft comment.
- **Scope is the organizing rule now, and it is duplicated on purpose.** Chips are screen-scoped; the two panel buttons (`/understand-changes`, `/code-review-diff`) read every patch; `/security-review` is a chip with merge-request scope, because a sink and the entry point reaching it are usually in different files. The runtime owns the prompt scope (`reviewCommandScope`) and the frontend owns a second copy of the same name list (`REVIEW_MERGE_REQUEST_SCOPED_COMMANDS` in `review-chat-composer.tsx`), because *it* decides whether to put `allDiffs` on the request. A name in one list and not the other is silent: either a pass told to "read every patch below" was sent none, or a screen-scoped turn now pays for the whole merge request.
- `/understand-diff` survives as an alias of the button rather than being deleted — the chip is gone, but typing it must not resurrect `Unknown command`. The old "Understand changes" prompt (Grep every changed file's importers and callers, "without relying on any pre-built knowledge graph") is gone: it contradicted `REVIEW_CHAT_SYSTEM_PROMPT`, duplicated the free TypeScript graph walk, and was the most expensive thing in the panel. It now reads the brief and greps *only* the changed paths the brief says the graph has no node for.
- Two solutions to this landed in parallel and were reconciled in the merge, so do not "restore" either half. `frontends/pixel_office/src/review/review-inline-prompts.ts` (from main) kept its shape — `id`/`label`/`icon`/`hint`/`prompt`/`expectSuggestions`, rendered as the button row — but its two prose prompts were replaced by the runtime's command names. Its `DIFF_ONLY_REVIEW_PROMPT` told the agent to reconstruct the diff itself (`git merge-base`, `git diff <base>...<source>`) with a fallback for "if git is not usable here"; that fallback is the normal case, not the edge, because the branch is never checked out — so its scope discipline (only added/modified lines, no full-file reads, no pre-existing findings, skip lint-catchable nits) was folded into the `/code-review-diff` expansion, where the patches arrive inline and git is not needed at all. Its `UNDERSTAND_CHANGES_PROMPT` ("without relying on any pre-built knowledge graph") is gone on purpose: that was the rejected option when the choice was put to the user.
- Run indicators use two different mechanisms deliberately. The chat buttons are derived from the transcript (`hasRunReviewCommand` — a *user* message whose text is that command), which costs no schema, survives a reload, and is reset by "Clear conversation" — exactly the scope the dot claims, since a cleared chat is a new CLI session. The header audit is not a chat message, so it persists `completedPasses` in the session document with the head SHA it ran against, and the dot goes amber when new commits land. Do not "unify" these: a transcript cannot record the audit, and a persisted flag for the chat buttons would survive a Clear and lie.
- `runtimeReviewSessionSchema` additions must carry `.default(...)`, never be required: `readReviewSession` `safeParse`s the stored file and treats a failure as "no session", which silently discards the reviewer's unpublished draft comments. `completedPasses` follows `chatMessages` for that reason, and `createEmptyReviewSession` in `state/review-sessions.ts` is the other half of every such addition — the type error there is the only thing that catches a missed one.

typing-into-a-restarted-claude-pty-has-no-ready-signal
- There is no "the agent is ready for input" event for Claude. `prepareAgentLaunch` installs `detectOutputTransition` only for codex (`agent-session-adapters.ts:983`) and cursor (`:1861`), so `agent.prompt-ready` never fires for a Claude session and the existing `deferredStartupInput` mechanism is codex-gated by design (`trySendDeferredCodexStartupInput` returns early on `agentId !== "codex"`). Anything that needs to type into a freshly started Claude PTY has to infer readiness — `postStartInput` does it with a quiet-gap timer re-armed on every output chunk (1.5 s) plus a 15 s max-wait for a session that renders nothing.
- The folder-trust prompt is the trap in that window: `continue\r` typed at it answers the prompt instead of the agent. Guarding on `hasClaudeWorkspaceTrustPrompt(workspaceTrustBuffer)` alone deadlocks, because trust auto-confirm fires **at most once per session** (`autoConfirmedWorkspaceTrust` is never reset) — trust text redrawn afterwards is never answered, so a guard that re-arms on it waits forever. Hence the deadline: withhold while the prompt is visible, send anyway once max-wait passes.
- `\r` submits; `\n` is Shift+Enter and only inserts a linebreak (`session-run-timing.ts:4-6`). The frontend's own injections use `\n` because they go through xterm, not the PTY — do not copy that for a direct `session.write`.
- Any teardown of an `ActiveProcessState` must go through `stopActiveProcessTimers`, not just `stopWorkspaceTrustTimers`: a settle timer that survives an exit writes into a dead PTY.

login-expired-is-cured-by-re-preparing-the-same-seat
- "Login expired · Please run /login" usually means a stale Claude Code OAuth pair, not a seat that needs a human. `POST /api/auth/accounts/{id}/launch-dir` → `prepare_account_dir` refreshes near-expiry tokens while preparing the dir (and since the 2026-08-25 fix, expired CC pairs too), so re-preparing the card's **own** seat and relaunching with `--continue` fixes it without any login. This is why `login-recovery-daemon.ts` prepares the seat *before* the restart — relaunching on the old config dir lands on the same login screen, which reads as "the recovery does nothing".
- The detector deliberately keeps the login-screen PTY alive (`session-manager.ts`, "Keep the PTY alive (Claude /login)"), so a recovery has to call `stopTaskSession` explicitly; it also clears `entry.restartRequest` and hands it to the reporter as `retryRequest`, which is the **only** copy left — a session hydrated after a runtime restart has none, and cannot be replayed at all.
- Detection covers two different renderings and used to catch only one: the banner "Login expired · Please run /login" matched, but the status line "Not logged in · Run /login" has no "please" and no trailing "to", so it fell through every pattern in `CLAUDE_AUTH_PATTERNS`. A session that only ever draws the status-line form was silently stuck.
- `markAuthFailoverOutcome` has to be called **after** `startTaskSession`, never before: the start writes a fresh summary with `authFailoverOutcome: null`, wiping anything recorded earlier.

a-relaunched-claude-session-loses-its-permission-mode-unless-the-flag-comes-back
- The permission mode is a *launch flag* in this runtime and nothing else: `--permission-mode auto` from the global `agentAutonomousModeEnabled` (default **on**), `--permission-mode plan` from the card's "Start in plan mode". Nothing observes the user cycling it with shift+tab, and every restart path replays the original `StartTaskSessionRequest` verbatim (`cloneStartTaskSessionRequest`), so a card the user had moved to plan/manual came back in auto — on crash auto-restart (10 per 5 s, `MAX_AUTO_RESTARTS_PER_WINDOW`), on login-expired same-seat recovery, on cross-seat failover and on a manual resume alike.
- `--continue` does not carry the mode. Claude Code says so itself, verbatim in its bundle: `--resume does not restore permissionMode — pass --permission-mode <mode> to match`. `~/.claude.json` has no per-project mode either, so re-passing the flag is the only way back into a mode.
- The recoverable record is the session transcript: Claude Code appends `{"type":"permission-mode","permissionMode":"..."}` on every change and stamps `permissionMode` on each user message. `claude-permission-mode.ts` tail-reads the newest `.jsonl` under `<CLAUDE_CONFIG_DIR|~/.claude>/projects/<cwd with / and . flattened to ->` — the same encoding `claude-cache-cleanup.ts` uses — and `claudeAdapter` prefers that over the configured defaults whenever the launch resumes. Do *not* scrape the PTY for it: there the mode is only a redrawn status line ("auto mode on" / "plan mode on") that ANSI wrapping can split.
- Seat launch dirs symlink `projects` → `~/.claude/projects` (and `prepareClaudeSkillScopedConfigDir` shares it too, `SHARED_SYMLINK_NAMES`), so pinning a card to a seat does not hide its transcripts — but read through the config dir anyway, since that is what the CLI will write to.
- The mode names are the CLI's, not ours: `["acceptEdits","auto","bypassPermissions","default","dontAsk","plan"]`, with `manual` as the display alias of `default`. Bypass is re-entered as `--dangerously-skip-permissions` (what Claude's own launcher emits) because `--permission-mode bypassPermissions` is additionally gated on the bypass dialog having been accepted.

task-base-ref-is-only-as-pinned-as-its-last-writer
- The task base ref lives in three places and the *registry* is the only one meant to be authoritative: `branch-registry.json` `entries[taskId].baseRef` (+ `baseCommit`), the board card's editable `baseRef`, and the ref a request happens to carry. `getTaskWorkspacePathInfo` prefers the registry, so reading the merge path top-down makes it look correct — the drift happens on the *write* side. `registerActiveBranch` used to overwrite the whole entry, and it runs on every worktree creation, so any reset/purge/restart re-seeded the "immutable" ref from the card (the statusLog is full of `deregister`/`register` pairs for exactly that reason). It is write-once now, and `op: "register-preserve-base-ref"` in the statusLog is the trace of a request that tried to change it.
- `rev-parse --verify <ref>^{commit}` accepts `HEAD`, so a floating ref used to pass creation validation and get recorded as the base — the live proof was `"baseRef": "HEAD"` on tasks in `akselos-dev`/`spm-3d-bi`, which means "merge into whatever is checked out". Use `resolveConcreteBaseBranch`/`isFloatingGitRef` (`workspace/git-utils.ts`) for anything that persists a ref. A worktree can therefore exist with an unusable base ref: `baseRefLocked` is false in that case *on purpose*, so the card's picker unlocks instead of freezing on a ref nothing can merge into.
- Locking a control in the UI is not locking the value: `task-inline-create-card`'s disabled dropdown still submitted `editTaskBranchRef || resolvedDefaultTaskBranchRef`, and that default is the home repo's current branch. `updateTask` now treats an empty draft ref as "keep the card's", because the editor seeds that field asynchronously from the server and a save can beat the fetch.
- Merging into a branch nobody has checked out needs a worktree of its own — git 2.34 is what ships here, so `git merge-tree --write-tree` (2.38+) is not an option. `runGitMergeBranchInTemporaryWorktree` does `git worktree add <mkdtemp> <baseRef>`, reuses `runGitMergeBranchAction` inside it (same `--no-ff` + abort-on-conflict), and removes it in a `finally`; it reports the *home* repo's summary because the caller pushes that into the home git panel. Anything spawning a worktree here also fires `post-checkout` — see [[worktree-hooks-fire-before-symlinks]].
- Chain followers have no worktree or registry entry of their own: pass `worktreeTaskId` (`resolveChainWorktreeOwnerTaskId`) on every task-scoped git call, or the lookup silently falls back to the follower's id and reports "Task worktree not found".

cline-home-is-half-legacy-half-live
- `~/.cline` is NOT a legacy directory. Only `~/.cline/kanban` was migrated forward (`state/runtime-home-migration.ts`), which is also all `getLegacyRuntimeHomePath()` points at — the `data/` sibling is the **live** Cline SDK home and is never migrated: `data/settings/providers.json` (built-in provider keys, `ProviderSettingsManager`), `data/settings/models.json` (user-added API seats — the OmniRoute/FPT.AI rows), `data/settings/cline_mcp_settings.json`, `data/db/sessions.db` (Cline chat history). `du` makes it look like pure garbage because sessions history dominates the size (314 MB of a 375 MB tree in the 2026-08-14 case).
- Deleting `~/.cline/data` therefore destroys every API seat and its key, and the failure is silent and indirect: `listApiSeats()` returns `[]`, and an empty seat list is exactly what four separate UI gates read as "feature not available" — Cline disappears from the card agent dropdown (`task-agent-model-picker.tsx`, `apiSeats.length > 0`), the "Subagents" row disappears from the account picker in the create dialog / inline card / card detail (`task-account-picker.tsx`), and "Default subagent seat" disappears from Settings. Nothing logs a cause; it reads as "someone deleted the subagent-seat feature". Resuming an existing Cline card fails with `Cline provider is selected but no Cline credentials are configured`.
- Recovery sources when it happens again: a pinned subagent seat's key survives in `backends/agent_stack/ccr-home/seats/<providerId>/config-router.json` (mode 0600, gitignored) because `stack/ccr-config.ts` wrote it there for the per-seat router; the *identity* of what was pinned survives in board state (`~/.agent/kanban/workspaces/*/board.json` → `subagentSeatProviderId` / `subagentSeatModelId`); OmniRoute's own `api_keys.key` column in `~/.omniroute/storage.sqlite` is plaintext. Rebuild seats through `createClineProviderService().addCustomProvider(...)` rather than hand-writing the JSON — `providers.json` is `ProviderSettingsManager`-internal. A restore only takes effect after a runtime restart: `ensureCustomProvidersLoaded` memoizes on the `models.json` path (`cline-sdk/sdk-provider-boundary.ts`).
- Related trap: `trpc/runtime-api.ts`'s `debugResetTargetPaths` ("reset all state") includes `~/.cline/data`, so that debug action also wipes seats and keys, not just boards.

pnpm-prepublish-quirk
- `frontends/pixel_office` depends on `"kanban": "file:../../backends/runtime"` (the CLI, for e2e). Under plain `npm install`, npm never builds/checks a `file:` dep automatically. Under pnpm, a `file:` dep gets packed like a publish target, so pnpm runs `prepare` AND `prepublishOnly` for `backends/runtime` on every `pnpm install` — which chains into `npm run build && npm run check` (full tsc + vite build + biome + the entire vitest suite). This means `pnpm install` at the repo root is slow and will surface any pre-existing lint/typecheck/test breakage as an install failure, even in files nobody touched.
- Migrating this repo from npm to pnpm (2026-08-01, see root CLAUDE.md changelog) surfaced three previously-dormant bugs that `npm install` never exercised: (1) `noUncheckedIndexedAccess` violations in `officeState.port.test.ts`/`layoutSerializer.port.test.ts` (array-index access needs `!`), (2) two zod v4 versions in the tree (`4.3.6` pinned by `backends/runtime`, `4.4.3` hoisted from other deps) making `RuntimeJackedSnapshot` (a `z.infer` type) look like "two different types with this name" in `office-jacked-semantics.test.ts` — fixed by pinning a single version via `overrides: { zod: 4.4.3 }` in root `pnpm-workspace.yaml` (pnpm reads overrides from there, not `package.json`), (3) `task-worktree.integration.test.ts` hardcoded the pre-rename `.cline` path instead of importing `KANBAN_RUNTIME_HOME_DIR_NAME` from `task-worktree-path.ts` (stale since the `~/.cline` → `~/.agent` rename).
- The user has a standing `Edit(**/package.json)` deny rule (any `package.json`, repo-wide) — this is enforced by Claude Code's own permission classifier, and it also blocks equivalent Bash workarounds like `npm pkg delete`/`npm pkg set` since those "accomplish the same package.json modification through a different tool." Any dependency/manifest change (versions, scripts, "workspaces" field, etc.) needs the user to do it, or needs a workaround that lives outside `package.json` (e.g. `pnpm-workspace.yaml` supports `overrides` and `allowBuilds` directly, so pnpm-specific config never needed a `package.json` edit).

spawned-services-lose-their-package-json-flags
- A child spawned by its entry script instead of its npm script silently loses everything the script configured. `omniroute-process.ts` runs `npx tsx scripts/dev/run-next.mjs` directly, so `backends/OmniRoute/package.json`'s `"dev": "node --max-old-space-size=8192 scripts/dev/run-next.mjs dev"` never applied and OmniRoute ran on V8's default old-space cap (~2 GB on a 7 GB box). Symptom seen 2026-08-14: `FATAL ERROR: Reached heap limit` at `2046 / 2084 MB` about 80 s in, right as `~/.omniroute/logs/application/app.log` printed `dev server listening on 8400 (turbopack)` — with a `node::sqlite::StatementSync::All` frame on top that sends you hunting for a runaway query. The DB is 5 MB; the sqlite frame was just the allocation that tipped an already-full heap. Fix is `NODE_OPTIONS` in the spawn env (`OMNIROUTE_MAX_OLD_SPACE_MB`, default 4096 — 8192 only trades a V8 OOM for the kernel OOM-killer here).
- The crash was invisible for the same reason twice over: `child.once("exit", (code) => { if (code !== 0 && code !== null) warn(...) })` says nothing for a signal death (V8 abort and OOM-kill both arrive as `code === null`), and the child's stdio went into an unbounded in-memory `errBuffer` that only got printed on a non-zero exit. Any supervisor here needs the `signal` argument, a capped buffer, and a restart — reuse `nextRestartDelayMs`/`shouldGiveUpRestarting` from `stack/stack-daemon.ts` rather than `superviseStackDaemon` itself, whose `buildStackEnv()` strips `ANTHROPIC_*` and whose pidfiles assume a stack root.

unbounded-git-reads-block-the-board
- Selecting a project used to hang the UI on a spinner for large repos (98k commits / 638 refs) because `runtime-state-hub.ts` **awaits** `workspaceMetadataMonitor.connectWorkspace(...)` before it sends the one `snapshot` message, and `connectWorkspace` awaited a full git refresh. Anything slow added to `refreshWorkspace` therefore delays first paint, not just metadata. It now races a 750 ms deadline and lets the real snapshot arrive over the existing `onMetadataUpdated` broadcast — which is also why the hub must send one `workspace_metadata_updated` immediately *after* registering the client, or a refresh landing in that window is broadcast to zero clients and lost.
- The poll is a self-rescheduling `setTimeout` (next tick at 3× the last refresh's duration, clamped to 1–15 s), not `setInterval`: at a fixed 1 Hz a 4-second refresh re-entered before the previous tick finished.
- In `use-git-history-data.ts`, `logRefs` must be memoized on **primitives**, not on the `activeRef`/`refs` objects. A refs refetch returns fresh objects even when nothing changed, and a new `logRefs` identity re-runs the effect that clears the commit list and reloads page one — so during an agent run the git panel silently re-fetched everything every tick and lost any pages the user had loaded.
- Per-read caps live in `workspace/git-limits.ts`; the two the wire needs (`GIT_LOG_MAX_COUNT_LIMIT`, `GIT_LOG_MAX_SKIP`) live in `core/api-contract.ts` because the zod schemas — and therefore the frontend's types — import them. Truncation is reported with `.optional()` flags, never `.default()`: `z.infer` yields the *output* type, so a default makes the field required on every existing construction site and test fixture.
- `runGit` distinguishes `outputTruncated` / `timedOut` / `aborted` from a real git failure. Before that, a commit whose patch exceeded the 10 MB `maxBuffer` surfaced as the generic "Failed to run Git Command" with no hint that a size limit was the cause.
- When a file's text is skipped for size, `contentOmitted` has to reach the UI: a null `oldText`/`newText` is indistinguishable from "file absent on this side", so a naive truncation renders the file as fully added or fully deleted — a *wrong* diff rather than a missing one.

stack-daemon-args-freeze-but-flags-do-not
- `stack-flags.json` is re-read per request by `server.py`, but a daemon's argv is fixed at spawn. Headroom is the one where that gap bites: `headroom-process.ts` passes `--anthropic-api-url http://127.0.0.1:3456` only when `ENABLE_CCR` was on **at its start**. Turning CCR off afterwards changed nothing about a running headroom, and `resolve_route` targets `HEADROOM_URL` whether CCR is on or off (both branches return it — only the chain *label* differs), so every request kept crossing the disabled CCR. The switchboard cheerfully reported `ENABLE_CCR: false` while 100% of traffic still went through it.
- Symptom seen 2026-08-13: `API Error: 400 Request format not supported` on every turn, including a brand-new task's first message. That string comes from the vendored CCR's `AnthropicInputProcessor` (`claude-code-router/dist/input/anthropic/processor.js`), not from Anthropic or Kanban. CCR auto-generates `ccr-home/.claude-code-router/config-router.json` on first start with `defaultProvider: codewhisperer-primary` and no credentials, so an unconfigured CCR fails *everything* that reaches it — `logs/ccr.log` fills with `Unknown model claude-sonnet-4-6, using default` → `Failed to add authentication token`.
- Debugging rule learned the hard way: the error naming "subagent" sent three rounds of investigation at the seat/subagent path, but the give-away was the timing — it failed instantly ("Brewed for 0s"), i.e. the *main* agent's own turn died before any subagent existed. Check whether the failing request is the parent's or a subagent's before picking a path. `ps -o args -p <pid of :8787>` shows headroom's real upstream in one command and would have ended it immediately.
- Fix: whoever launches headroom now records its real upstream in `logs/headroom.chain` (`ccr` or `direct`) — `superviseStackDaemon`'s `chainState` for the runtime, an explicit `printf` in `activate-stack.sh`, cleared by both plus `stop-stack.sh`. `resolve_route` skips a headroom whose marker says `ccr` while the flag is off, surfacing `headroom:8787 (still chained to disabled ccr, skipped — restart it)` instead of silently honouring neither. A missing marker means "unknown" and keeps the old trust-the-flags behaviour, so a hand-started headroom is not misjudged.
- Two independent CCR bugs share that one error string, so fixing either alone still looks broken: (1) the chain-staleness above, and (2) the vendored CCR rejects `system` as a plain string — valid, documented Anthropic shape, and exactly what Claude Code's subagent dispatches send — accepting only an array of content blocks. `read_subagent_route` in `server.py` normalizes it for seat-routed traffic only; the direct/headroom paths accept either form and are left alone.

the-dsh-headless-task-is-a-positional-and-the-patch-layer-only-overrides
- The `dsh` launcher parses **only** `--profile`, `--patch` (repeatable), `--resume`, `--help`, `--version`, `--dump-config`, `--dump-default-config`, and hands everything from the first token it does not recognize to the booted profile. The headless app's own grammar is `dsh --profile headless [options] [task...]` with `-h/--help` as its **only** option — the task is a variadic positional, "multiple words are joined by spaces". `orchestrator-launch.ts` shipped `--profile headless --patch <p> --cwd <cwd> --force --prompt <text>`, which dies at the app's parser with `error: unknown option '--cwd'`, so **no Custom Agent card could ever run**. Rule: the prompt is the last, bare argument; never add a flag to that argv without finding it in `dsh --profile headless --help` first.
- A patch layer addresses **existing** rows by id; new rows must go under `- insert:` (see `@deepseek-ai/dsh-headless`'s own `cordis.patch.yml`). `config/orchestrator/pixeloffice.patch.yml` had three bare top-level entries with new ids. Measured: with the bare form `--dump-config` exits **0** and the composed tree contains **zero** `cursor_agent` rows — the providers are dropped silently, with no warning anywhere. Under `insert:` they appear. `dsh --profile headless --patch <file> --dump-config` composes without booting and is the only cheap way to check this; two `--patch` overlays compose together, which is how the generated Flowise overlay rides alongside the shipped one (JSON is accepted, since YAML is a superset).
- Out-of-tree plugins resolve from the dsh installation first and then from the **profile's** `node_modules` (`$DSH_HOME/profiles/headless`), never from `$DSH_HOME` itself — `dsh-home-setup.ts` used to `npm install` into the wrong directory while `runtime.orchestrator.status` cheerfully reported "installed". Install through `dsh plugin --profile headless add <pkgs>` (confirmed in `dsh --help`: "forwarding the remaining arguments to pnpm in the profile directory").
- **Never install dsh packages with `--legacy-peer-deps`.** The plugin graph wires itself through *peer* dependencies — `dsh-app-boot` peer-depends on `@deepseek-ai/cordis-plugin-group`, `-loader`, `-include` and `cordis` with only `-hmr` marked optional — and that flag makes npm skip peers outright. The resulting tree installs cleanly, exits 0, and then every `dsh` invocation dies with `ERR_MODULE_NOT_FOUND: Cannot find package '@deepseek-ai/cordis-plugin-group'`. npm did not backfill the peer on a later plain `npm install` either; it had to be named explicitly.
- The **npx fallback in `resolveDshBinary()` is not usable as a launch path.** `npx --yes @deepseek-ai/dsh --help` resolves the ~100-package harness tree before running anything: measured at 219 s to a V8 heap OOM under the default 2 GB cap, and still unfinished after 10 min with a 5 GB cap. `runDshPluginAdd` therefore refuses `viaNpx` (it runs unawaited on every runtime boot), and `installed` in `runtime.orchestrator.status` requires a non-npx binary — npx exists on nearly every machine, so counting it made the Agents sidebar report the Custom Agent ready wherever dsh was absent. `PIXELOFFICE_DSH_BINARY` pointed at a local `npm install --prefix` tree is the working escape hatch when a global install is not possible.
- dsh **does** speak MCP: `@deepseek-ai/dsh-mcp-client`, one plugin row per server (stdio or streamable-http), tools registered as `mcp__<serverName>__<rawName>`, `serverName` constrained to `[A-Za-z0-9_-]{1,32}` and unique across live instances. There is no `dsh-tool-mcp` package — searching for one is what makes this look impossible and sends you down the "delegate to `cursor_agent` so *it* can hold the MCP" path. It has no auto-reconnect, so keep `failOnStartupError: false` and treat a dead shim as "tools present but failing" until the session restarts.
- **The orchestrator does not need a DeepSeek key.** dsh mounts `@deepseek-ai/dsh-llm-pi-ai` — a generic multi-provider adapter whose catalog ships `google`, `anthropic`, `openai`, `xai`, `groq`, `mistral`, `deepseek` and which accepts any OpenAI-compatible gateway as configuration — but ships that row with **no config**, so it registers no routes, while `agent-default-model` points at `deepseek-official`. `orchestrator-llm-patch.ts` overlays both (they are existing ids, so bare overrides, *not* `insert:`) to aim dsh at this repo's own `/api/flowise-llm-proxy/<provider>`, which strips the caller's `authorization` and injects the pinned Manager seat's credential. A full headless turn on the Cursor seat was verified end to end with no API key present. `PIXELOFFICE_DSH_LLM_PROVIDER=deepseek` restores the old behaviour; without a key that path reaches `dsh: MISSING_CREDENTIAL: llm-deepseek: …`, which is the useful "argv and patches are fine, credentials are not" checkpoint.
- Two traps in that overlay. (1) **Declare models outright.** The seat routes serve ids pi-ai's catalog does not know — `auto/best-coding` is OmniRoute's, not OpenAI's — and an undeclared id fails at resolution with `UNKNOWN_MODEL: pi-ai provider "openai" has no configured model "auto/best-coding"` before any request goes out. (2) **Give the route an `apiKeyEnv` anyway.** pi-ai resolves the reference per request and fails a configured-but-unresolvable one with `MISSING_CREDENTIAL`; the launch exports a placeholder the proxy then discards.
- Proxy route health measured 2026-09-01, and it is not uniform: `/cursor` and `/openai` answer `GET /v1/models` and `POST /v1/chat/completions` with 200 (same OmniRoute upstream), `/anthropic` has its seat bearer accepted by Anthropic, but **`/gemini` returns `403 ACCESS_TOKEN_SCOPE_INSUFFICIENT`** — the forwarding is correct and the seat's OAuth token simply is not scoped for `generativelanguage.googleapis.com`. That breaks the Flowise Gemini node too, not just dsh, and no amount of dsh-side configuration fixes it.

worktree-hooks-fire-before-symlinks
- Task worktrees are created with `git worktree add --detach` in `src/workspace/task-worktree.ts:534`. The runtime symlinks gitignored deps (`node_modules`, `backends/jacked/.venv`, `frontends/pixel_office/dist`) into the new worktree only AFTER `worktree add` returns, via `prepareNewTaskWorktree` (line 551). But `git worktree add` performs a checkout, which fires the repo's `post-checkout` hook (`core.hooksPath=.githooks`) synchronously — so any hook runs against a worktree that has NO deps yet.
- If a hook exits non-zero, `git worktree add` reports failure, the runtime returns the hook's stderr as the task error (task-worktree.ts:535-543), and `prepareNewTaskWorktree` never runs — the worktree is left registered but symlink-less, so every subsequent task in it also fails. Symptom seen 2026-08-01: `.githooks/post-checkout` → `scripts/rebuild-ui-if-changed.sh` ran `npx vite build` with no `node_modules`, dying with `ERR_MODULE_NOT_FOUND: Cannot find package '@tailwindcss/vite'`. Looks like a pnpm/dependency problem (three prior sessions chased it as one) but is not — there is no per-worktree install step by design; deps arrive via symlinks the hook failure prevents.
- Rule: any repo git hook that could fire during `worktree add` must guard for absent deps (e.g. `[ -d node_modules ] || exit 0`) and must not hard-fail on a fresh worktree. Fix applied: `scripts/rebuild-ui-if-changed.sh` early-exits when `frontends/pixel_office/node_modules` is missing.

TypeScript principles
- No any types unless absolutely necessary.
- Check node_modules for external API type definitions instead of guessing.
- Prefer SDK-provided types, schemas, helpers, and model metadata over local redefinitions. For things like Cline SDK reasoning settings, use the SDK's source of truth whenever possible instead of recreating unions, support checks, or shapes in Kanban.
- NEVER use inline imports. No await import("./foo.js"), no import("pkg").Type in type positions, and no dynamic imports for types. Always use standard top-level imports.
- NEVER remove or downgrade code to fix type errors from outdated dependencies. Upgrade the dependency instead.

Code quality
- Write production-quality code, not prototypes
- Break components into small, single-responsibility files. 
- Extract shared logic into hooks and utilities. 
- Prioritize maintainability and clean architecture over speed. 
- Follow DRY principles and maintain clean architecture with clear separation of concerns.
- In `web-ui`, prefer `react-use` hooks (via `@/kanban/utils/react-use`) whenever possible
- Before adding custom utility code, evaluate whether a well-maintained third-party package can reduce complexity and long-term maintenance cost.

Architecture opinions
- Avoid thin shell wrappers that only forward props or relocate JSX for a single call site.
- Prefer extracting domain logic (state, effects, async orchestration) over presentation-only pass-through layers.
- Do not optimize for line count alone. Optimize for codebase navigability and clarity.

web-ui Stack
- Kanban web-ui uses Tailwind CSS v4 for styling, Radix UI for accessible headless primitives, and Lucide React for icons.
- Custom UI primitives live in `src/components/ui/` (button, dialog, tooltip, kbd, spinner, cn utility).
- Toast notifications use `sonner`. Import `{ toast }` from `"sonner"` or use `showAppToast` from `@/components/app-toaster`.

Styling mental model
- Use Tailwind utility classes as the primary styling system. Prefer `className` over inline `style={{}}`.
- Prefer Tailwind classes over adding custom CSS in `globals.css` when possible. Conditional Tailwind classes via `cn()` are better than CSS overrides for state-driven styling (e.g. selected/active variants). Reserve `globals.css` for things Tailwind can't express: complex selectors (sibling combinators, attribute selectors), app-level layout glue, or styles that genuinely need to cascade.
- Only use inline `style={{}}` for truly dynamic values (colors from props/variables, computed positions from drag-and-drop, runtime-dependent dimensions).
- The design system tokens are defined in `globals.css` inside `@theme { ... }`. Use Tailwind utilities that reference them: `bg-surface-0`, `text-text-primary`, `border-border`, etc.

Misc. tribal knowledge
- Kanban's native Cline agent is powered by the installed `@clinebot/core` and `@clinebot/llms` packages plus the local `src/cline-sdk/` boundary layer, so when Cline behavior is unclear, inspect those packages and `src/cline-sdk/` for the real implementation details.
- Kanban is launched from the user's shell and inherits its environment. For agent detection and task-agent startup, prefer direct PATH checks and direct process launches over spawning an interactive shell. Avoid `zsh -i`, shell fallback command discovery, or "launch shell then type command into it" on hot paths. On setups with heavy shell init like `conda` or `nvm`, doing that per task can freeze the runtime and even make new Terminal.app windows feel hung when several tasks start at once. It's fine to use an actual interactive shell for explicit shell terminals, not for normal agent session work.
- If CI hangs on Node 22 after tests seem to finish, suspect a live subprocess or SDK-host startup path before assuming a slow test body. Read `.plan/docs/node22-ci-hanging-tests-investigation.md` before repeating that investigation. `test/runtime/cline-sdk/cline-task-session-service.test.ts` was the big prior culprit because a unit-style suite was still booting the real Cline SDK host.
- When Kanban runs on a headless remote Linux instance (for example over SSH+tunnel), native folder picker commands may be unavailable (`zenity`/`kdialog`). Treat this as a normal remote-runtime limitation and use manual path entry fallback instead of requiring desktop packages.
